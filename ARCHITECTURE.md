# Architecture

## Overview

SKILL.md Inspector is a Visual Studio Code extension for validating and inspecting Agent Skill metadata. It analyzes files named exactly `SKILL.md`, publishes editor diagnostics and quick fixes, and provides per-skill and workspace-level reports.

The implementation is local and deterministic. It does not call network services, use telemetry, or invoke an LLM. Parsing, validation, scoring, collision detection, portability checks, and report-model construction are ordinary TypeScript modules; VS Code-specific modules adapt those results to diagnostics, commands, edits, tree items, and webviews.

The shipped extension is a single CommonJS bundle at `dist/extension.js`. VS Code loads that bundle and calls `activate` when a Markdown document is opened or a workspace contains a `SKILL.md` file.

## Main Runtime Components

### Extension Host Adapter

`src/extension.ts` is the runtime entry point. During activation it:

- creates the shared `DiagnosticsProvider`;
- registers Command Palette handlers;
- registers the Explorer tree view and its refresh command;
- watches for creation and deletion of `SKILL.md` files;
- registers Markdown quick fixes;
- validates skills when documents open, change, or save;
- refreshes visible results when extension configuration changes.

Edits are debounced by 300 milliseconds before revalidation. All listeners, providers, watchers, commands, and pending timers are tied to the VS Code extension context for cleanup.

### Parsing and the Skill Document Model

`src/parser/parseSkillFile.ts` creates the normalized `SkillDocument` used by later stages. Parsing is split into focused operations:

- `parseFrontmatter` reads YAML frontmatter, records source ranges, and reports structural or YAML parse errors.
- `parseMarkdownLinks` uses Unified, Remark, and Unist traversal to extract Markdown links from the body with source locations.
- `discoverResources` scans the conventional `references/`, `scripts/`, `assets/`, and `templates/` directories.
- `withResources` marks discovered files as referenced when a relative Markdown link resolves to them.

Text parsing itself is pure. Filesystem access begins when resources are discovered or link targets are checked.

### Analysis and Validation Core

`analyzeSkill` is the main single-file pipeline:

1. Parse the file content into a `SkillDocument`.
2. Discover and attach bundled resources.
3. Run all validation rules for the selected profile.
4. Return the normalized document and tool-neutral diagnostics.

`runAllValidations` combines independent checks for frontmatter, name, description, links, resources, and body structure. Diagnostics use repository-defined severities, ranges, codes, and optional quick-fix metadata; `diagnostics/mapping.ts` converts them into VS Code diagnostics only at the UI boundary.

Description quality is a related but separate concern. `quality/` detects action verbs, trigger and boundary phrases, concrete artifacts, vague wording, and intent placement. `computeTriggerQuality` turns those findings into a 0-100 score and label. `buildImprovedDescription` creates deterministic suggestions by retaining the current wording and adding missing trigger or boundary clauses, or by offering a template for a poor description.

### Profiles and Configuration

`readConfig` reads the `skillMdInspector.*` settings and resolves one of four profiles: `generic`, `vscode`, `claude`, or `codex`. A profile defines name and description limits plus profile-specific rules. User-configured length limits are applied as overrides to the selected profile.

The same effective profile is passed into editor validation, skill reports, workspace analysis, and exported indexes so those surfaces normally agree on rule thresholds.

### VS Code Diagnostics, Commands, and Edits

`DiagnosticsProvider` owns one VS Code diagnostic collection. It delegates analysis to `analyzeSkill`, maps the returned diagnostics, and publishes them for an editor document. The workspace validation command finds every `SKILL.md` through the VS Code workspace API and applies the same provider.

Command modules are thin handlers for these workflows:

- validate the active skill or all workspace skills;
- insert a starter `SKILL.md` template;
- show a per-skill report;
- suggest and optionally apply a local description rewrite;
- show the workspace report;
- export `skills.index.json`.

`SkillCodeActionProvider` reruns the core analysis for the active document, selects diagnostics intersecting the requested range, and translates their quick-fix metadata into `WorkspaceEdit` operations. Fixes can modify frontmatter or body text, rename a skill directory, create a missing linked file, or add a resource link.

### Workspace Analysis

Workspace intelligence starts with `discoverSkillPaths`, which recursively scans a root directory while skipping dependency, version-control, build-output, and VS Code test directories. `analyzeWorkspace` analyzes each readable skill and produces `WorkspaceSkill` records containing diagnostics counts, Trigger Quality, portability, and a resource graph.

It also compares every pair of skill descriptions. Collision detection tokenizes descriptions, builds smoothed TF-IDF vectors for the current corpus, computes cosine similarity, and reports pairs at or above `0.40`. Similarity bands classify collisions as Low, Medium, or High risk.

Portability is a heuristic summary across the four supported profiles. Baseline validation errors fail all profiles; additional Claude and Codex checks can downgrade compatibility to a warning. The resource graph classifies bundled and linked files as referenced, unreferenced, missing, remote, or absolute and flags scripts, binary formats, and files at least 256 KiB.

### Reports and Explorer Tree

The Explorer tree, workspace report, and skills-index export share `computeWorkspaceAnalysis`, the VS Code-facing workspace-analysis entry point. The tree lazily computes and caches an analysis until a refresh-triggering event clears it.

Report construction is separated from presentation:

- report-model modules convert analysis results into display models;
- renderer modules create escaped HTML;
- webview panel classes own one reusable panel for each report type.

Both report webviews are read-only and have scripts disabled. The single-skill report shows validation and Trigger Quality details. The workspace report shows skill summaries, collision results, profile portability, and resource graphs.

## Data Flow

### Live Editor Validation

1. VS Code opens, changes, or saves a document.
2. `extension.ts` filters for a file named `SKILL.md` and reads the effective configuration.
3. `DiagnosticsProvider` passes the in-memory text and filesystem path to `analyzeSkill`.
4. The parser creates a `SkillDocument`; resource discovery attaches nearby bundled files.
5. Validation rules return tool-neutral diagnostics.
6. The adapter maps ranges and severities to VS Code objects and replaces the document's diagnostic collection entry.
7. When requested, the code-action provider derives edits from the same analysis and diagnostic metadata.

### Per-Skill Report

1. The command reads the active editor's unsaved text.
2. It runs `analyzeSkill` with the selected profile.
3. `buildReportModel` adds diagnostic counts, file lists, and Trigger Quality results.
4. The HTML renderer escapes and formats the model.
5. `SkillReportPanel` displays the HTML in a reusable, script-disabled webview.

### Workspace Report, Tree, and Export

1. `computeWorkspaceAnalysis` chooses the first open workspace folder.
2. The filesystem scanner discovers `SKILL.md` paths below that root.
3. Each file is read from disk and analyzed into a `WorkspaceSkill`.
4. Cross-skill collision detection runs after all per-skill records are built.
5. The resulting `WorkspaceAnalysis` feeds the Explorer tree or workspace report.
6. For export, `buildSkillsIndex` selects the public fields, adds a generation timestamp, and the command writes `skills.index.json` at the workspace root.

Workspace analysis reads saved files from disk; unlike active-editor analysis, it does not include unsaved editor changes.

## Key Design Decisions

- Core analysis is independent of `vscode`. This keeps rules reusable and allows most behavior to be tested in a Node process without launching an Extension Development Host.
- Diagnostics are the shared contract between rules and editor fixes. Rule modules identify a problem and attach fix metadata; the VS Code adapter owns mutations.
- Profile rules and length overrides are resolved before analysis rather than read throughout the core modules.
- Workspace analysis builds a complete in-memory result and shares it across tree, report, and export representations.
- Reports generate static escaped HTML and disable webview scripts because their surfaces are informational.
- Collision and portability results are deterministic heuristics, not semantic or execution-based guarantees.
- The local description improvement command deliberately uses templates and heuristics. The `llm/` interface and experimental setting are placeholders and are not connected to runtime behavior.

## External Dependencies and Integrations

Runtime dependencies are deliberately small:

- VS Code Extension API for lifecycle, configuration, diagnostics, edits, commands, files, tree views, and webviews;
- `yaml` for frontmatter parsing;
- `unified`, `remark-parse`, and `unist-util-visit` for Markdown link extraction;
- Node filesystem and path APIs for discovery, resource checks, and workspace analysis.

Build and development dependencies include TypeScript, esbuild, Vitest, ESLint, Prettier, VS Code type definitions, and `@vscode/vsce` when packaging through `npx`. The extension has no remote service integration at runtime.

## Build and Validation Notes

- Required VS Code engine: `^1.90.0`.
- TypeScript targets ES2022 with strict checking, unused-symbol checks, and no emit.
- esbuild bundles `src/extension.ts` and its dependencies as CommonJS for Node 18, leaving the host-provided `vscode` module external.
- Production builds write a minified `dist/extension.js`; watch builds also emit a source map.
- Vitest runs `test/**/*.test.ts` in a Node environment.
- The Extension Development Host launch configuration runs `npm run build` before loading the current workspace as the extension under development.

Contributor validation commands are:

```bash
npm run check-types
npm run lint
npm test
npm run build
```

Packaging runs the production build through the `vscode:prepublish` script before creating a VSIX.

## Known Constraints

- Workspace reports, the Explorer tree, and index export analyze only the first open workspace folder. The separate workspace-validation command uses VS Code's workspace-wide file search and can therefore cover more than that first folder.
- Workspace discovery and analysis use synchronous Node filesystem operations on the extension host. Very large directory trees or large skill collections can block the host while a report or tree analysis is computed.
- The tree caches its analysis until explicit refresh, skill creation/deletion, a `SKILL.md` save, or relevant configuration changes. Changes to a bundled resource alone do not directly refresh it.
- Workspace analysis reads files from disk, so unsaved `SKILL.md` edits are visible to live diagnostics and the per-skill report but not to the tree, workspace report, collision analysis, or export.
- Collision scores depend on the descriptions present in the analyzed workspace corpus. They indicate lexical overlap, not whether an agent will actually choose the wrong skill.
- Portability checks are a small set of local heuristics; they do not execute skills in VS Code, Claude, Codex, or another agent environment.
- Remote links are classified and checked syntactically but are not fetched. Relative-link and resource checks depend on the local filesystem state.
- The experimental LLM review setting, provider interface, prompts directory, and providers directory are inert. No LLM-assisted review is currently implemented.
